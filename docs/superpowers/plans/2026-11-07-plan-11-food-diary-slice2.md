# Plan 11: Food Diary Slices 2 and 2b: the Diary Day, Local Dates, Frozen Day Targets, Edit, Copy, Quick Add, and Meal-Slot Management

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The account holder keeps a food diary on Android and web. Each local day shows meal slots (four defaults, renamable, up to six), entries that carry their own nutrient snapshot, edit, move and delete, copy a meal or a day, quick add, and totals and remaining against that day's frozen target, all computed by the API. The Diary replaces the History tab.

**Architecture:**
- **API first.**
  - One migration, `0009`, adds `accounts.timezone`, `diary_days` (the frozen per-day target), `meal_slots`, and the slice-2 `meal_logs` columns, with back-fills.
  - Three new feature folders:
    - `app/features/meal_slots/` (slot reads in slice 2, management in 2b);
    - `app/features/diary/` (frozen days, pure day and week aggregation, the day, week, status and recents routes);
    - `meals` extended in place (log v2, update, copy).
  - Diary entries **are** `meal_logs` rows, so the Android offline queue and `client_id` idempotency keep working.
- **Then the shared step:** golden diary fixtures (generated by a script, hand-checked), `layouts.json` (`history` becomes `diary`), i18n, the analytics allow-lists, and `just contract`.
- **Clients** (Android ∥ web), in two paired tasks for slice 2 and one for 2b. Clients render `remaining`, `progress`, totals and the suggested slot exactly as the API returns them.
- Targets stay information: `analyze()` and the verdict modules never import `diary`, `meal_slots` or `targets`.

**Tech Stack:** as Plan 10. API: Python 3.13, FastAPI, SQLAlchemy 2 async + Alembic, pytest, `decimal`, `zoneinfo` (+ `tzdata`). Android: Flutter, Riverpod 3, go_router, drift (the offline queue), the generated `smartnutri_api`. Web: Next.js 16, TanStack Query, next-intl, `@smartnutri/api-client`. Tests: pytest, flutter_test, Vitest, Playwright.

**Spec:** `docs/research/food-diary/FEATURE_SPEC.md` (binding).

## Rulings made while writing this plan

Existing names and shapes win over the spec where they already exist. Each ruling is also cited inline where it applies.

**Migration and schema**
- **E1 (one migration):** `0009_diary_days_slots_entries` (`down_revision = "0008_diary_goal_settings"`) holds:
  - `accounts.timezone` and `diary_days` (spec 5.11 put these in 0008; Ruling D1 moved them here);
  - `meal_slots` (including `client_id`, so slice 2b needs no migration);
  - the slice-2 `meal_logs` changes.

  Spec numbers from `0010` on stay valid.
- **E2 (slice-2 columns only):** `meal_logs` gains `local_date`, `meal_slot_id`, `source_kind` (closed set `product`, `off`, `quick_add`), a nullable `grams`, `food_snapshot`, `updated_at`, and the `fibre_g` nutrient key. These arrive with slices 3–4, which widen `ck_meal_logs_source_kind` and `ck_meal_logs_ref`:
  - `food_id`, `custom_food_id`, `recipe_id`;
  - `quantity` and `unit`, with their checks.
- **E3 (FK action):** the entry → slot FK is `ON DELETE NO ACTION`, not the spec's `RESTRICT`.
  - `RESTRICT` is checked row by row inside a cascade, so deleting a member (whose slots and entries both cascade) would fail.
  - `NO ACTION` still refuses a hard delete of a used slot.
- **E4 (one set of default bands):** the 5.12 windows are both the slot defaults and the back-fill bands: Breakfast 04:00–10:59, Lunch 11:00–15:59, Snacks 16:00–18:59, Dinner 19:00–03:59.
  - Spec 5.1's "before 11:00 Breakfast" would put 00:00–03:59 in Breakfast, which contradicts "the same bands".
  - Windows are inclusive whole minutes and may wrap past midnight.
  - The defaults live in `app/features/meal_slots/defaults.yaml`. They are not a health threshold, so no clinician mark.
  - The migration copies them as constants, and a test keeps the two equal.

**Days, dates and targets**
- **E5 (today live, past frozen):** while `health_data` is active, today's `diary_days` row is recomputed and upserted on every read or log of today.
  - So settings, weight, birth-year and time-zone changes reach it without hooks.
  - A past row is never recomputed; only `partial_logged` changes.
  - A row is computed only with `health_data`. A past day with no row is `none` and is never back-filled.
  - `targets_get` for a past date now returns the frozen row, replacing D1's "always none", with `rate_options: []`.
- **E6 (frozen storage):** the target numbers go in columns.
  - The unrounded explanation decimals go into `inputs` as strings, plus `rate_kg_per_week`, `missing_fields` and `yaml_version`.
  - `frozen.from_row` rebuilds a `TargetResult`, so `to_targets_out` stays the only mapping, and redaction always uses the *current* `numbers_display`.
- **E7 (time zone):**
  - `accounts.timezone` (default `Asia/Kolkata`) is set by a new `PUT /v1/me/timezone` (`me_timezone_put`; error `422 timezone_invalid`). `MeOut.timezone` is added.
  - Clients send the device zone when it differs from `MeOut.timezone`: web via `Intl.DateTimeFormat().resolvedOptions().timeZone`, Android via the `flutter_timezone` package. If either fails, nothing is sent.
  - It is not health data, so it needs only sign-in.
  - `tzdata` joins the API dependencies (`core/time.py` notes the container may lack zone data).
  - Changing the zone never moves a stored `local_date`.
- **E8 (no client date maths):** clients never work out a date boundary.
  - `DiaryDayOut.today` is the account's local today.
  - `MealIn` gains `local_date`, for logging onto a past day: `eaten_at` becomes that date at the current local clock time, capped at now. `local_date` and `eaten_at` together are `422 validation_error`.
- **E13 (remaining and progress):**
  - `remaining = target − eaten`, 1 dp half-up; negative means over.
  - `remaining` is `null` when there is no target, when that nutrient is incomplete, or when it is hidden.
  - With nothing logged, totals are `null`, `remaining` equals the target, and `progress` is `0` (as `protein_left_g` does today).
  - `progress = eaten ÷ target`, 2 dp. When hidden, it is rounded to the nearest 0.25 (the shape only).
  - Clients show `diary.over` with the absolute value of a negative `remaining`. That is formatting, not arithmetic.
- **E14 (consent status):** `targets_status` is `consent_required` whenever `health_data` is not active, even with no settings (spec 6.2, literal). The day still loads.
- **E15 (summary):**
  - `Totals` and `IncompleteNutrients` gain `fat_g`, `carbs_g` and `fibre_g`.
  - Days group by the stored `local_date`; the default `date` is the account's local today.
  - The protein target comes from that day's frozen row. A past day with no row falls back to the legacy rule.

**Members and routes**
- **E9 (family logging stays):**
  - `meals_log`, `meals_list`, `meals_summary` and `meals_delete` keep accepting any member of the account, because Plan 6 shipped family logs.
  - Every **new** route (`meals_update`, `meals_copy`, `diary_*`, `meal_slots_*`) uses `targets_service.resolve_member`: another account's member is 404, and a non-primary member is `422 diary_member_not_enabled`.
  - Because `meal_slot_id` is NOT NULL, non-primary members get hidden default slots (from the back-fill, and lazily on log). This departs from the last bullet of 5.12.
  - `member_id` becomes optional (default: the primary member) on `meals_log` and `meals_list`.
- **E10 (PATCH null = unchanged, as D3):** the generated Dart client sends every unset field as `null`.
  - `MealPatch` therefore treats `null` as "unchanged".
  - The slot rename clears through explicit `clear_custom_label` and `clear_time_window` flags.
- **E11 (quick add):**
  - Shape: `source_kind = quick_add`, `grams` null, and the optional name stored in `product_name`.
  - The name is user text: never sent to analytics, logs or prompts.
  - Sugars, saturated fat and salt are null, so those totals are incomplete.
  - Limits: energy `0 < x ≤ 5000`, each macro 0–500 g, fibre 0–200 g. Missing energy is `422 quick_add_energy_required`.
  - Editable through `PATCH quick`, on `quick_add` entries only.
  - A bad reference keeps the existing code `invalid_product_ref` (the spec's `invalid_food_ref` arrives with slice 3).
- **E12 (copy):**
  - `client_id` is required. Each copy's `client_id` is `uuid5(request.client_id, str(source.id))`, so a retry returns the same rows (200) and a double tap creates nothing.
  - `eaten_at` is `to_date` at the source entry's local clock time, capped at now.
  - The slot is `to_slot_id`, or else the source entry's own slot.
  - Copies reuse the source snapshot and never fetch the product again.
  - `to_date` must be between `today − 30` and today. Outside that range: `date_too_old` or `date_in_future`.
  - `ratelimit.consume` gains `n: int = 1`, so each copied entry counts against the `meal_logs` limit.
- **E16 (week):**
  - `DayTile` adds `bands` (the existing `NutrientBands`).
  - The API returns `averaged_days`, `averages_incomplete` and `protein_met_days`.
  - The History weekly family share moves into the week view's menu.
- **E17 (History → Diary):**
  - The Diary shows the primary member only (Q9); the History member switcher is not carried over.
  - `/history` redirects to `/diary` on both clients.
  - Tabs follow spec 7.10; the home cards are unchanged (D14).
  - The `today_targets` Home card switches from `meals_summary` to `diary_day_get` for eaten and remaining (D20's follow-up).
- **E18 (recents):** the list excludes quick adds and is de-duplicated by product id or barcode, newest first. It holds at most 30 items from the last 90 local days, and puts the given slot's items first.
- **E19 (Android offline):**
  - Only new entries, including quick adds, go through the queue. Edit, delete, copy and slot management need a connection (existing offline copy).
  - Queue schema v2 adds `mealSlotId`, `localDate`, the quick fields and `displayName`.
  - A pending row shows its name and "waiting to sync", never a number.
  - With no loaded slot list, the slot picker is hidden and the API picks the slot.
- **E21 (redact every MealOut):** every `MealOut` (log, update, copy, list) is redacted with its member's `numbers_display`. Slice 1 left `meals_list` unredacted.
- **E22 (status code):** `meal_slot_not_found` is 404 whether the id comes in the path or the body, like `member_not_found`.

**Slot labels and scope**
- **E20 (slot labels):**
  - Labels are unique among a member's active slots by `lower(custom_label)` only. The API can't compare the translated default names.
  - Stored trimmed, otherwise exactly as typed.
  - Length is counted in Unicode code points (Dart `runes.length`, JS `[...s].length`). Control characters are refused.
  - Deleting an archived slot returns `{result: "archived"}` (idempotent). There is no un-archive in v1.
- **E23 (scope):** slice 2 is spec row 2 in full, including the week view, partial days and recents. The brief's list is a subset; the spec is binding.
  - Generic-food search is slice 3; until then the Add-food search segment opens the existing product search.
  - The analytics `method` enum (shared with `scan_started`) grows by the diary methods.
- **E24 (ADR):** this plan adds ADR 0023, "Diary days: local dates and frozen daily targets".

## Global Constraints

Health-app rules (root `AGENTS.md`, non-negotiable):
1. **The rules engine decides; targets are information.** Clients never compute a total, a remaining value, a progress fraction, a local date or a default slot. `analyze` responses are byte-identical with and without diary data.
2. **Never invent nutrition data.** An unknown nutrient is `null`, never 0. A total over entries with any unknown value is marked `incomplete`, and `remaining` is then `null`. Quick-add blanks stay unknown.
3. **Unknown is not safe.** Incomplete and unknown use the grey "not enough data" style, never green. Targets and "over" never use verdict colours or the danger token.
4. **Thresholds live in data.** No new health number in this plan. Slot windows are presentation data in `meal_slots/defaults.yaml`.
5. **Secrets stay server-side.** Nothing new is public config.
6. **No health data in analytics** (spec 6.8).
   - Allowed: only `diary_entry_added {method}` and `diary_day_viewed {}`.
   - Never sent: any nutrient, target, remaining, hidden state, custom slot label, slot count or quick-add name.
7. **No medical claims.** `diary.disclaimer` and "Pending clinician review" wherever a target or remaining number shows.
8. **Strings only in `packages/i18n`** (en, hi, mr). The hi and mr machine drafts are listed in `packages/i18n/NATIVE_REVIEW.md` under "Plan 11". Custom slot labels and quick-add names are user text and never pass through i18n.
9. **Never hand-edit generated code.** `just` is not installed for agents: run the justfile recipe lines by hand (`.superpowers/sdd/RULES-FOR-AGENTS.md`).
10. **Feature parity.** A slice is done only when the API, Android and web all ship it and the diary fixtures pass on all three.

Slice rules (spec sections in brackets):
- **Solo only (Q9):** see Ruling E9. [1.4, 6]
- **Consent (Q13):** the diary works on `terms`. The new prefixes `/v1/diary` and `/v1/meal-slots` gate on `terms` by prefix. The `targets` part of the day and week views checks `health_data` inside the handler. [6.6]
- **Hidden numbers (Q7):** the API redacts every new surface.
  - `hide_energy` nulls every energy field.
  - `hide_all` also nulls every macro, sugar, salt and fibre value.
  - Portions (grams, servings) and slot structure stay.
  - Progress keeps quarter-step shapes.
  - Clients show no digit for a hidden value anywhere, including toasts and pending queue rows. [6.2]
- **Neutral tone** [7]: progress uses the brand colour, over uses a neutral token, and there are no streaks, ratings or "good day" labels.
- **Contract:**
  - `operation_id` is `<feature>_<action>`.
  - Errors use `ErrorEnvelope` with an `error.<code>` key in en, hi and mr.
  - Write routes depend on `current_account_row`.
  - The consent gate runs before `limit()`.
- **Decimals:** API arithmetic is in `Decimal`, rounded half-up for display only. Stored snapshots stay unrounded (Plan 6 F1).
- **Commits:** Conventional Commits with a scope, ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Run `gitleaks protect --staged --no-banner` before each commit. Never push.

## Review Focus

1. **The local-date boundary.** Cases:
   - an entry at 23:59:59 and one at 00:00:00 local;
   - an account in `America/New_York` logging at 22:00;
   - a time-zone change mid-week;
   - an entry logged offline before midnight that syncs after midnight.

   Expected: each entry lands on the local date of its `eaten_at` in the account zone at log time, and a zone change never moves a stored date. Owned by:
   - Task 1: `test_local_date_of_dst_and_midnight`;
   - Task 4: `test_log_local_date_uses_account_zone`, `test_offline_entry_keeps_eaten_at_day`;
   - Task 7: `test_timezone_change_keeps_past_dates`.
2. **Unknown counted as 0.** A quick add with kcal only, or an OFF product with no energy value, on a day with a target. Expected:
   - the totals are lower bounds marked incomplete;
   - `remaining` and `progress` are `null` for those nutrients;
   - clients show the grey chip, never "X left".

   Owned by:
   - Task 5: fixtures `day_quick_add_kcal_only`, `day_incomplete_energy`;
   - Tasks 9 and 11: `incomplete nutrient shows the grey chip, not a number`.
3. **Hidden numbers leaking through a new surface.** With `hide_all`, a digit can still show through:
   - the `meals_log` response, a copy toast or a slot subtotal;
   - week averages, a recent item, or the "X over" line;
   - an Android pending quick-add row.

   Expected: no digit for energy or macros anywhere. Owned by:
   - Task 7: `test_hidden_numbers_every_diary_surface`;
   - Tasks 9 and 11: `hide_all leaves no digits on the day`;
   - Tasks 10 and 12: `hide_all leaves no digits on the week`, `copied toast shows count only under hide_all`;
   - Task 10: `queued entry shows waiting to sync without numbers`.
4. **Copy double-tap and future times.** Two scenarios:
   - The user taps "Copy yesterday" twice, or the response is lost and the client retries. Expected: one set of copies (200 on the retry).
   - The user copies yesterday's 20:00 dinner to today at 09:00. Expected: `eaten_at` is capped at now, never a 422.

   Owned by Task 6: `test_copy_retry_returns_same_rows`, `test_copy_double_tap_creates_once`, `test_copy_future_clock_time_capped_at_now`.
5. **The Android queue across the upgrade and slot removal.** Two scenarios:
   - Entries queued by the old app (queue schema v1) must sync after the update.
   - An entry queued for a slot that is archived before sync. Expected: v1 rows migrate and sync with no slot (the API picks one); the archived case comes back `meal_slot_archived` and the app asks the user to pick another meal.

   Owned by Task 10 (`queue v1 rows migrate and sync`) and Task 15 (`archived slot on sync asks to pick again`).

  - A repeated `client_id` returns the stored row with 200.
  - Six active slots → `422 meal_slot_limit` with `details {max: 6}`.
  - A duplicate `lower(label)` among active slots → `422 meal_slot_label_duplicate`. Details are empty, because the label is never echoed.
  - The new slot takes position = max active position + 1.
- **Rename:**
  - An archived slot → `422 meal_slot_archived`.
  - `clear_custom_label` on a default slot restores its key name. On a custom slot → `validation_error`.
  - A value together with its clear flag → `validation_error`.
- **Reorder:** the ids must be every active slot exactly once, else `validation_error {fields: ["body.ids"]}`. An unknown or foreign id → 404. Positions are rewritten to 0..n−1 in one transaction.
- **Archive:**
  - The last active slot → `422 meal_slot_last_active`.
  - Any `meal_logs` row on the slot → set `archived_at` (`archived`); none → delete the row (`deleted`).
  - An already archived slot → `archived` (idempotent).
- **Routes**, all through `resolve_member`; create, rename, reorder and archive use `limit("diary_writes")`:
  - `POST /v1/meal-slots`: `meal_slots_create`, 201 or 200.
  - `PATCH /v1/meal-slots/{slot_id}`: `meal_slots_rename`.
  - `PUT /v1/meal-slots/order`: `meal_slots_reorder`.
  - `DELETE /v1/meal-slots/{slot_id}`: `meal_slots_archive`.
